# AGENTS.md

## Source of truth

- `SPEC.md` is the full product spec and the authoritative task list. Follow its milestones (M0–M9) in order.
- `PROGRESS.md` is the progress log and the substitute for git history (see "Git & progress log" below). Read it before starting any task and update it after every finished, verified one.
- Reading is routed by task type (see "Reading routes" below) — do not read the whole SPEC when a task touches one §. Do not add features from §6 (out of scope).
- `PERF.md` is a **reference backlog** for memory/build-speed work, not an autonomous queue: the owner picks an item, and the agent executes it only when asked. Its §0 has the task details and the owner gates.
- `DEBTS-verification.md` and `DEBTS-functional.md` are the live debt lists (see "Debts" below): checks awaiting a HUMAN, and deliberate simplifications / postponed decisions. Read both at session start and at task end — and ASK about them.
- `PROBLEMS.md` is the agent-friction log — literally a PURE entry log: the agent never reads a line of it and never edits it by hand; entries go in only through `scripts/log_problem.sh` (prepended at the very top, newest first). The entry template lives in the "Agent-friction log — PROBLEMS.md" section below, not in the file.

## Project layout — the filesystem is the source of truth

No file tree is kept in the docs (owner decision 2026-11-11): agents list the
actual files with their own tools when needed, and docs only carry the rules
that survive file churn. The durable rules:

- A module's tests live in a sibling `tests.rs` file (see "Tests"): `src/canvas.rs` ↔
  `src/canvas/tests.rs`.
- New subsystem → a child module of the module that owns the state/behavior (for `App` state that
  means `src/app/<name>.rs`). Never grow `app.rs` with a new subsystem.
- A new or removed file is reported in the `PROGRESS.md` entry of the same task (what and why);
  no tree or layout list needs updating anywhere.
- Do not add top-level directories or build tooling (no `xtask`, `just`, scripts) without
  asking the owner. The owner-approved exceptions: CI (2026-11-11, see "Repo facts") and
  the friction-log writer `scripts/log_problem.sh` (owner-requested 2026-11-20, see
  "Agent-friction log — PROBLEMS.md").
  The build is `cargo` + `scripts/verify.sh` + `trunk` + the flake.

## Tests — separate files, always

Hard rules. They exist so production files stay readable and an agent can add tests without
touching behavior code.

1. **No inline test modules.** Never write `#[cfg(test)] mod tests { ... }` inside a source file.
   The module file ends with exactly:

   ```rust
   #[cfg(test)]
   mod tests;
   ```

   and the tests live in `<module>/tests.rs` next to it:

   - `src/canvas.rs` → `src/canvas/tests.rs`
   - `src/app/placement.rs` → `src/app/placement/tests.rs`
   - `src/text.rs` → `src/text/tests.rs`

   The file is a CHILD module: start it with `use super::*;` (or an explicit
   `use super::{a, b};`) and test private items directly.
2. **Never widen visibility for a test.** No `pub(crate)`/`pub` just to reach code from a test.
   If a test cannot reach it, it is in the wrong module — move the test, not the visibility.
3. **No crate-root `tests/` directory.** The crate is a single binary (no lib target), so
   integration tests cannot import it. Keep tests as in-crate unit tests. Adding a lib target is a
   structural change that needs the owner's OK first.
4. **Every fix/feature ships with a test**, in the same task, in the module that owns the behavior.
   A bug fix starts from a regression test that fails before the fix. Never delete a test to get
   green; update it in the same edit when behavior intentionally changes. Docs-only rounds
   (a diff touching only `.md` files) ship no tests — see "Commands" (owner request 2026-11-20).
5. **Test what the spec promises**, not implementation details. Prefer small pure helpers over a
   full egui frame; if behavior is only reachable through `App`, extract the math into a testable
   helper in the same task.
6. **Style.** `#[test]` only (no async, no new dev-dependencies). Names are behavior sentences in
   `snake_case`, no `test_` prefix. Arrange–Act–Assert with blank lines between blocks.
   `expect("what must hold")` for invariants; `unwrap()` forbidden everywhere. No filesystem,
   network, sleeps or wall-clock in tests.
7. **Size guard.** Keep `tests.rs` under ~300 lines. Past that, split by topic: `tests.rs` keeps
   only `mod <topic>;` declarations and the files move to `src/<module>/tests/<topic>.rs`.
   **Owner-locked exception (2026-11-17):** `src/app/scenarios/tests.rs` — the whole-app
   scenario suite — is exempt from BOTH this guard and the 500-line file guard: it grows
   scenario by scenario on the owner's request, splitting it is NOT a debt and is never
   proposed, and editing it without the owner's explicit permission is forbidden
   ("editing without the owner's permission is forbidden" — the file's own header says the same;
   `scripts/rules.sh` skips it in the size-guard loop).
8. `cargo test` must pass before a task counts as done, and `cargo clippy --all-targets` lints the
   test files too.

The agent never commits; the owner commits locally using the titles proposed below. **Git is not the progress channel here — `PROGRESS.md` (repo root) is.**
- **The owner sent a `russet.zip`? Use it immediately (owner request 2026-11-16):** do NOT run `git pull` or `git clone` first — unpack the .zip into the workspace and start working from it right away; a delivered .zip is the owner's signal that it is the freshest state and takes priority over any sandbox copy or remote (it also saves setup time). Snapshot the unpacked tree as the patch base BEFORE the first edit (`git add -A; git write-tree > /tmp/base_tree; git reset`), even when the .zip ships without `.git` — a throwaway `git init` keeps the delivery patch possible.

- After finishing AND verifying a task or milestone: insert one entry at the top of the "Log" section of `PROGRESS.md` (newest first) — date, `M<N>:`-style title (or a short title for non-milestone work), what changed and in which files, how it was verified (commands + result), and what the owner still must check manually. Update the status snapshot and warnings in the same edit.
- **Commit titles (owner request 2026-11-10):** whenever a task leaves changes that will later go into a commit, ALWAYS propose a commit title for them — one short imperative line in the repo's existing `git log` style (multi-part changes joined with `;`), e.g. `Add Eyedropper, Line/Curve, Shape, Text tools and History/Layers windows`. State it in TWO places: the `PROGRESS.md` log entry (a `Commit title:` line) AND as the **very last line of the chat reply to the owner** (owner request 2026-11-10: always in the same findable place, easy to copy). **Backtick wrapping (owner request 2026-11-13):** the title's canonical form is the whole line wrapped in a pair of backticks — backtick + title + backtick — in BOTH places: in the chat UI a backticked string is click-to-copy, so one click puts the exact title on the owner's clipboard; rules.sh rule 6 prints the log field with the backticks kept, so the hand-over string stays verbatim end-to-end, and it warns NOT WRAPPED when the newest entry's title lacks them. The agent never commits itself (see above).
- **Log-entry budget (owner request 2026-11-10):** one entry = at most ~20 lines with the fixed fields (What / Files / Verified / Owner-checks / Commit title). Anything durable learned during a task MUST move to its canonical home in the SAME edit — a new egui quirk → the quirks section below, an owner decision or behavioral law → `SPEC.md` §3.x, a module fact → that module's docstring — and the log entry only references it.
- **Log compaction:** when the "Log" section of `PROGRESS.md` grows past ~150 lines, move all but the newest 3–5 entries verbatim into `PROGRESS-archive.md` (read it only via grep when investigating history) and note that in the Log heading. The status snapshot carries a one-line verification stamp (`fmt/clippy clean, cargo test: N green — date`), updated in the same edit.
- Never record work as done in `PROGRESS.md` before its verification commands actually pass.

## Debts — pending human checks & functional debts

Two files carry what would otherwise rot silently inside PROGRESS.md log entries
(owner decision 2026-11-13):

- **`DEBTS-verification.md`** — checks only the OWNER can do: Windows `cargo run`
  click-throughs, browser passes, `nix build`, doc wording sign-offs. A log entry's
  `Owner-checks` line is history; the LIVE tracking of what is still unverified
  lives in the file.
- **`DEBTS-functional.md`** — deliberate simplifications, postponed work and open
  decisions (placeholders, postponed CI jobs, "later" items).

Hard rules:

1. A debt is born in the SAME edit as the task that creates it: every new
   owner-check item and every deliberate simplification lands in the matching file
   immediately, with its birth date. Never leave a debt only in the log entry.
2. **Ask, don't accumulate (owner request 2026-11-13).** At session start and at
   task end, surface the open items of BOTH files to the owner in ONE batched list
   and ask which are human-verified / which decisions are made. Never assume a
   check happened; never remove an item silently. Items unchecked for over a week
   are flagged explicitly as stale.
3. A verified item gets `Status: verified <date>`; a paid functional debt gets
   `Status: paid <date>`; both are dropped at the next compaction. The historical
   record stays in the PROGRESS.md entries.
4. `scripts/rules.sh` is the automated reminder: it reports PROGRESS.md size, its
   Log-section size, RESOLVED-but-unarchived warnings and the count of live
   owner-checks (report-only).
5. PROGRESS.md `Warnings` holds ACTIVE blockers only; a warning moves to
   `PROGRESS-archive.md` in the SAME edit that resolves it. The Log keeps only the
   newest 3–5 entries (the compaction rule above); `rules.sh` warns when the
   budgets (~200 file lines, ~150 log lines) are exceeded.
6. **Ordering (owner request 2026-11-16).** Open items in BOTH debt files are
   written sorted: verification checks (V) first, then functional debts (F),
   then anything else; within each group, NEWEST birth date first (the same
   newest-first convention as the PROGRESS.md Log). A closed item leaves the
   open table for the Resolved/Paid section in the SAME edit — it never
   lingers there.
7. **The ask lists only the 4 newest (owner request 2026-11-18).** When surfacing
   open debts to the owner — the batched session-start/task-end list and every
   chat reply — write out ONLY the 4 newest open items, newest first (rule 6's
   order applies inside the four). The FILES keep every open item; nothing is
   dropped, only the ask stays scannable.

## Agent-friction log — PROBLEMS.md (owner request 2026-11-20, pure-log form)

`PROBLEMS.md` is LITERALLY a log: it holds entries and nothing else — no
header, no template; it starts straight with its newest entry. The agent
NEVER reads a single line of it (not for context, not for dedup, not to check
the format) and never edits it by hand: entries go in ONLY through the
owner-requested `scripts/log_problem.sh <entry-file>`, which PREPENDS the
entry's bytes verbatim at the very top (newest first) and BYTE-CHECKS after
the write that the previous content survived intact below the new entry — a
mismatch restores the backup and fails without touching the log. Nothing in
the log can therefore be deleted or rewritten by an agent (the owner's
explicit permission is the only door). Keep the entry file OUTSIDE the repo
(e.g. `/tmp/entry.md`) — a file inside the worktree would leak into the
delivery artifacts.

The ENTRY TEMPLATE (abstract — fields are guidance, not a form; style may
vary entry to entry, the content carries the meaning): a
`### <date> — <one-line what>` heading, then a few bullets — what happened
(expected vs actual), how it showed up, what it cost (minutes / rebuilds /
retries / "nothing material"), and, when visible, what could improve
("none, one-off" is a valid answer). Anything qualifies: a command that lied
or hung, a quirk that cost a rebuild, a doc that missed the needed fact, a
wrong assumption, "worked as intended but felt fragile". Writing an entry is
bookkeeping, never a task; a durable fact learned along the way still moves
to its canonical home (SPEC §, AGENTS.md, SANDBOX.md, the module docstring)
in the same edit — the log entry stays raw. The owner reads the file and
reviews what to improve only when HE decides to.

## Delivery ritual — artifacts sent to the owner

The owner applies the work locally, so every finished round ships the project as files, and it is not known in advance which form will fit the owner's local state. Always prepare BOTH, under FIXED names so every session delivers the same files (owner request 2026-11-10):

- **`russet.zip`** — the full project tree, NEVER containing `.git`, `target/` or other build junk. It applies on any owner state: unpack and replace the tree.
- **`russet.patch`** — `git diff <base-commit>` with new files intent-to-add (`git add -N` first, so they are included), base commit stated in the reply. Prepare it ONLY when `.git` is present in the sandbox copy; without git there is no patch — say so plainly in the reply and `russet.zip` is the only artifact. When the owner has already committed the previous delivery locally (the normal state — his commits never reach the sandbox), the base is NOT an old sandbox SHA: snapshot the PRE-EDIT tree first (`git add -A; git write-tree > /tmp/base_tree; git reset` — a tree object, no commit or ref is created) and diff against it; the reply states that the patch applies on top of the owner's latest local commit, which must byte-match the previous delivery.

Before calling the delivery ready: with git, apply the patch onto a clean copy of the base commit and byte-compare the result with the working tree AND with the unpacked zip — all three must match; without git, byte-compare the unpacked zip with the working tree. Always regenerate the artifacts in the same session as the changes — never re-send an artifact from an earlier round. Print the sizes and sha256 checksums of the delivered files so the owner can verify the download. **No target artifact is ever part of this ritual**: the warm-target store is retired for now (owner decision 2026-11-17 — see "Commands — Session start"). The mechanics are automated (owner request 2026-11-17): `bash scripts/deliver.sh <base-ref> <out-dir>` stages the tree, builds both artifacts, runs BOTH byte-compares and prints the checksums itself — use it for every delivery; the agent still writes the `PROGRESS.md` entry and states the base commit + checksums in the chat reply (when the out-dir is the chat's download directory, the reply links the files).

The final chat reply MUST state the suggested commit title verbatim (owner request 2026-11-13: it was repeatedly left out), backtick-wrapped so the chat UI's click-to-copy hands the exact title to the owner (owner request 2026-11-13; see "Commit titles" above). Copy it from the newest PROGRESS.md log entry's `Commit title:` field — rules.sh rule 6 prints it as a REMINDER at every done-gate with the backticks kept, so the last verify.sh run hands over the exact string to paste as the reply's last line. The reply lists ONLY the newest delivery's title — ONE title per reply (owner request 2026-11-20: the former "if the delivery covers several rounds, list every round's title" clause grew out of a ONE-TIME request that the agent mis-recorded as a standing rule — "это была единичная просьба и агент решил записать это как правило"; the owner keeps the older titles' list himself — "я и так их записываю" — so re-listing them every reply is noise, not hand-over). If a round is docs-only and adds no log entry, say that no commit title is proposed.

## Dependencies — approval flow (owner decision 2026-11-12)

The former hard ban ("do not add dependencies") is replaced by an explicit approval
flow, so a worthy crate is used instead of being re-invented as an in-house wheel:

1. The agent never adds a dependency silently. When a task needs one, it stops and
   asks the owner FIRST — this includes bumping an existing dependency beyond its
   pinned version.
2. The proposal must state: (a) the problem and why it is real; (b) the candidate
   crates with trade-offs (maintenance, MSRV, weight, transitive dependencies,
   runtime libs for `flake.nix`, wasm impact); (c) the no-dependency alternative
   and whether skipping it means re-inventing the wheel; (d) the agent's
   recommendation.
3. The owner picks an option or rejects the request. Only then does the code land:
   the version pinned in `Cargo.toml` (SPEC §1 style), `Cargo.lock` updated in the
   same task, runtime libs added to `flake.nix` `runtimeLibs`, and README/SPEC
   updated in the same edit when build/run docs change.
4. An opt-in capability ships as a feature-gated optional dependency
   (`dep:name` under a `[features]` flag) so the default build stays light.

## eframe/egui 0.37 API quirks (verified against installed crate)

- `eframe::App` implements `fn ui(&mut self, ui: &mut egui::Ui, frame: &mut eframe::Frame)`; there is no `update` method.
- `egui::CentralPanel::default().show(ui, ...)` takes `&mut egui::Ui`, not `&egui::Context`.
- `egui` is not a direct dependency: `use eframe::egui;` (or fully qualify `eframe::egui`).
- Keyboard-focus guard is `ctx.egui_wants_keyboard_input()`, not `ctx.wants_keyboard_input()`.
- `Ui::id()` is deprecated; use `Ui::scope_id()`.
- `egui::Grid` floors EVERY column at `interact_size.x` (40 pt) regardless of the widgets inside (`grid.rs` `set_min_col_width(col, widget_rect.width().max(min_cell_size.x))`) — a compact grid of narrower widgets (e.g. 28 pt tool buttons) silently grows wide columns and a huge visible horizontal gap while the row gap obeys `spacing().y` (caught by pixel measurement 2026-11-18: 18 pt vs 6 pt). Fix: `.min_col_width(widget_width)` on the Grid builder.
- Panels are unified: `egui::Panel::top(id)` / `bottom` / `left` / `right`; there is no `TopBottomPanel`/`SidePanel`.
- Menu bar is `egui::MenuBar::new().ui(ui, |ui| { ui.menu_button(...) })`; there is no `egui::menu::bar`.
- The theme API SPLITS the choice from the active style: `egui::Theme` = {Light, Dark} only — there is NO `FollowSystem` variant (a compile error, caught 2026-11-18). The Dark/Light/System choice is `egui::ThemePreference`: `Context::set_theme(impl Into<ThemePreference>)` stores it, and `Context::theme()` returns the RESOLVED active `Theme` (what the icon atlas keys on); `Context::system_theme()` mirrors the OS.
- egui 0.37's color picker has NO hex/RGB text entry ANYWHERE: `color_picker_hsva_2d` renders only the R/G/B(/A) `DragValue` row (`srgba_edit_ui` — no text field), and `color_edit_button_srgba`/`_hsva` have none either (the hex format exists only in the accessibility `current_text_value`). russet adds its own per-well hex field under the picker (`windows/palette_window.rs::color_swell_button`, owner request 2026-11-19): the raw text lives in egui's `IdTypeMap` keyed per well (a frame-rebuilt string would fight the caret), it is re-seeded from the color on popup open / outside changes, parsed on edit through `launch.rs::parse_hex_components` (the launch-flag syntax, one primitive), and canonicalized `#RRGGBBAA` on blur. The syntax is JUNK-TOLERANT (owner request 2026-11-19: every non-hex-digit character is stripped before parsing, an optional `0x` prefix dropped first; the remaining DIGIT COUNT picks the form — 3 `RGB`, 4 `RGBA`, 5 `RGBAA`, 6 `RRGGBB`, 7 `RRGGBBA`, 8 `RRGGBBAA`; the owner calls the 5-vs-7 RGB-digit asymmetry deliberate). The short forms' alpha fallback is a per-well SEED alpha snapshotted with the text (the same re-seed branch): a live-typed longer entry passes THROUGH alpha-carrying prefixes (typing `FF7F00` hits the 5-digit form at `FF7F0`, whose own alpha briefly applies), and without the seed that prefix's alpha would leak into the final 6-digit color.
- Tool windows/panels are drawn with `egui::Window::new(...).show(&ctx, ...)`; input over them must not paint on the canvas (use response hover/occlusion, not raw pointer position).
- Title-bar drag of a `Window` is detected via `ctx.read_response(area_id.with("__title_click"))` (the same id `window.rs` uses internally).
- `Window::new(title)` derives the window's Id FROM THE TITLE (`window.rs` on `Window::new`: "This is true even if you disable the title bar") — a changing, hidden or EMPTY title MUST come with an explicit `.id(…)` or the identity (stored position!) resets; `Window::id`'s doc: "Required if the title changes, or is shared with another window". To keep the title BAR but hide only the LABEL, pass an EMPTY title string: `title_ui` builds the bar (button atoms + drag strip) from the bar itself regardless of the text, so `Window::new("").id(…)` renders a label-less bar (caught 2026-11-18, the Tools window — v4's `title_bar(false)` removed the whole bar, the owner wanted only the label gone). `title_bar(false)` itself removes the ✕/collapse buttons too, but the window STAYS movable: `WindowDrag::TitleBar` "silently falls back to `Self::Anywhere`" for title-bar-less windows.
- An auto-sized window's TITLE STRIP does not participate in the window's size (`title_ui` allocates a ZERO-width advance rect horizontally — `window.rs` "We may not allocate in the horizontal direction as that would break auto sizing") and is free to PAINT wider than the window itself. The strip's fixed width with BOTH buttons and an empty title = 2 button atoms (each as wide as the Heading row height — 20.7 pt at the default 18 pt Heading font) + 4 `item_spacing.x` gaps (8 pt each) + the strip frame's inner margin (the window frame's 6 pt per side) = 85.4 pt, against the Tools window's outer 76 pt (the 62-pt grid + frame margins) — the strip painted ~11 pt past the window's right edge and the ✕ landed half outside it (owner report 2026-11-19; pixel-measured headless AND under Xvfb). The per-window lever is `Window::title_frame(...)`: its inner margin is the strip's padding (egui re-applies the active `weak_bg_fill` on top of it itself, so a `Frame::NONE`-based title frame keeps its background), and `Margin` fields are `i8` in 0.37. russet's chosen fix (owner v6 2026-11-19, "variant A2"): `tools_window_builder` feeds `title_frame` with `Frame::window(&ctx.global_style())` whose `inner_margin.left/right` are zeroed (`app/windows.rs::tools_title_frame`) — the strip's minimum (73.4 pt) fits the grid-width window, so the strip paints EXACTLY the window's width and both buttons sit inside; the vertical padding stays (the strip's height, fill and rounded corners unchanged — the owner's variant A, `Margin::ZERO`, additionally shrank the strip vertically and shifted the first-open position; NOT picked). The regression test (`windows/tests/tools_strip.rs`) measures it headless: the strip's drag response `area_id.with("__title_click")` spans from the collapse ICON's right edge to the close ICON's left edge, and each ICON is its button atom shrunk by `(atom − icon_width) / 2` per side, so the atoms' outer edges are `click.min_x − (heading_row_height + icon_width) / 2` and `click.max_x + (heading_row_height + icon_width) / 2` — both must stay within the window (the default frame put the ✕ atom's edge ~4.4 pt past it).
- Window COLLAPSE (the strip's ▼ button or a title double-click): the state lives in `CollapsingState` under `area_id.with("collapsing")` (public path: `egui::collapsing_header::CollapsingState` — NOT `egui::CollapsingState`) and is `store`d EVERY frame right after the window content — so after `Window::show`, `CollapsingState::load(ctx, …)` already sees THIS frame's toggle. `Window::show` returns `Some(InnerResponse { inner: None })` exactly while the collapsing body is closed (openness 0; the show doc states it), which makes `response.inner.is_some()` the per-frame "body shown" flag — russet's settings-panel hide-while-collapsed guard keys on it (owner request 2026-11-19). A window with a stored `pivot` re-anchors AROUND the pivot point when its size changes: collapsing a `pivot(LEFT_CENTER)` window moves its top edge DOWN by half the height delta, so a click position taken from the expanded window misses the collapsed strip.
- Headless `Context::run_pass` texture counting (the atlas-lifecycle test): the FIRST pass uploads the app textures PLUS egui's font atlas (the count = the atlas's icon textures + 1 font — currently 33: 8 tool + 8 shape + 2 line + 6 select + 8 tree icons; owner request 2026-11-20 added the Select family, 2026-11-21 the tree row-size set); a ppp change re-uploads only the app textures (the font atlas uploads once); a theme change uploads exactly 1 (the font atlas follows the theme) — so a rebuild-vs-no-op discriminator is the count vs the expected app-texture count, not `== 0`.
- `egui::Rect` has NO `min_x`/`min_y`/`max_x`/`max_y` shorthand FIELDS — the only fields are `min: Pos2` / `max: Pos2`; the edge accessors are the METHODS `left()/right()/top()/bottom()` (plus `width()/height()/center()/…`). Caught 2026-11-20 (six `E0609` errors cost a cold gates-test compile in the gap test; logged in PROBLEMS.md).
- To move a `Window` programmatically (e.g. when a resize repositions a floating window), load `AreaState::load(ctx, area_id)`, call `set_left_top_pos`, and persist with `memory.areas_mut().set_state(LayerId::new(Order::Middle, area_id), state)` right after `Window::show` — `Window::current_pos` is discarded every frame in title-bar mode, and builder position calls would fight the drag.
- `Window::default_pos` applies only while the window's `AreaState` has no stored `pivot_pos` (fresh session; eframe's `persistence` feature is compiled in — owner request 2026-11-23 — but the AUTOMATIC save channels are off, `persist_window: false` in main.rs + `persist_egui_memory() -> false` in app.rs, so every launch is still fresh: window geometry and egui Memory are never written or read, and the one saved setting (the Mouse4/5 mode, §3.14/SPEC) is a single flat key that carries no window state. The feature's one unavoidable side effect is the startup-created data dir — `~/.local/share/russet` on Linux, `%APPDATA%\Russet\data` on Windows — EMPTY for a user who never decided a setting). Pair it with `.pivot(Align2::…)` to pin a corner/edge instead of the left-top: `pivot(LEFT_BOTTOM)` + `default_pos(content_rect().left_bottom())` = flush bottom-left. `set_left_top_pos` converts through the stored pivot, so §3.11 repositioning stays correct with any pivot.
- eframe 0.37 `persistence` save mechanics (verified against the installed crate, the settings round 2026-11-23): there is NO request-save API — `App::save` runs on the 30-s autosave (`App::auto_save_interval()`, overridable) and at exit (`save_and_destroy`), so a changed setting lands within ≤30 s or at quit. Native `FileStorage` marks the file dirty on EVERY `remove_string` but only on a VALUE CHANGE for `set_string`, and `flush` writes `app.ron` only while dirty — therefore: a repeated remove of an ABSENT key would still dirty+write the file every autosave (guard: remove only when `get_string` says the key is present), and an unchanged set is free. `eframe::set_value`/`get_value` (RON) need serde, which eframe does NOT re-export — adding `serde` to Cargo.toml would be a dependency-approval-flow decision; the zero-dependency path is plain `set_string`/`get_string` with hand-encoded values (russet encodes the Mouse4/5 mode as `"ask"`/`"always"`/`"never"` under `"settings/mouse_side_buttons"`). On web every Storage key becomes its OWN localStorage entry (and `persist_egui_memory: false` keeps `egui_memory_ron` unwritten).
- An `auto_sized()` `Window`/`Resize` sees `available_width()` = the whole `content_rect` on its FIRST layout pass (its `default_size` is INFINITY clamped to the screen), and its `desired_size` never shrinks below the first frame (`max(last_content_size)`). Any content width derived from `available_width` therefore opens the window screen-wide AND grows it one row-overflow per frame forever — the Layers window smeared past the main window this way (owner report 2026-11-13; full write-up at `app/layers_window.rs::LAYERS_DEFAULT_WIDTH`). Fixed-width rows + `default_width` (Layers now) or only content-hugging widgets (Tools/Palette) are stable; `available_width`-derived widths are safe ONLY in windows with a stored `default_width` (Tool Log).
- A PLAIN `Window` (not `.auto_sized()`) opens at egui's default outer size **340×420** (`window.rs` `Resize::default().default_size([340.0, 420.0])`), and its content's measured size never shrinks below what the first frame measured. Any scope that inherits the whole remaining available rect — e.g. a bare `ui.with_layout(...)` row — is anchored into that empty space (right/bottom per its layout), keeps the content min-size huge, and the dialog stays tall with its buttons detached below the fields (owner report 2026-11-15: dialogs stretched toward the main-window bottom edge; regression tests in `app/dialogs/tests.rs`). Bound such rows with `allocate_ui_with_layout(vec2(available_width(), row_height), …)` — safe in windows with a stored default width, NOT in `.auto_sized()` ones (quirk above). For dialogs that must ARISE centered on EVERY open (owner request 2026-11-15), `app/dialogs.rs::dialog_window` pins `pivot(CENTER_CENTER)` + `default_pos(content_rect().center())` and every close path calls `forget_dialog_position`, which overwrites the stored `AreaState` with a fresh one so the next open consumes `default_pos` again (`default_pos` is only ever consumed while the stored `pivot_pos` is None) — the dialog re-centers when reopened, yet stays draggable while open; the reset must run AFTER `Window::show` on the closing frame (the dialog's early-return skips all later frames, so nothing re-stores a position). egui's `Area::anchor(Align2, offset)` is the other tool — it is re-applied every frame AND makes the window immovable (`movable(false)`); right for permanently-fixed HUD-like windows, too rigid for dialogs, and it overrides egui's cascade `automatic_area_position` that would otherwise drop a new window slightly right/below of the existing ones.
- A headless-egui pass (`Context::run_pass`) paints NOTHING on a window's first pass — every shape arrives culled to `Shape::Noop` (the window is measured before its stored geometry exists); real shapes (`Shape::Text` runs included) appear from the SECOND pass on. Content-assertion tests (e.g. `app/dialogs/tests.rs::render_about_texts` joining `galley.job.text` per `Shape::Text`, recursing into `Shape::Vec` nests) must therefore run 2–3 passes and read the LAST one — the same "egui sizes a fresh window on the frame after its first layout" rule the plumbing tests follow.
- Textures die with their handles: `TextureManager` keeps a per-texture retain count, `TextureHandle::drop` decrements it (`TextureManager::free`), and a texture nobody holds is removed the SAME frame — the renderer then draws NOTHING where the stale `TextureId` was sampled (no warning, no white quad — silent emptiness). `Context::load_texture_cached` returns a handle like any other load; storing only the `TextureId` and dropping the handle freed the tool-icon atlas mid-run and rendered empty Tools buttons (caught by the visual-driver screenshot, owner request 2026-11-18). ALWAYS keep the `TextureHandle` alive for as long as the `TextureId` is sampled (russet: `app/tool_icons.rs::Atlas::handles`). Headless-egui tests do NOT catch this — the headless pass never rasterizes.
- Custom OS cursors: `Context::set_cursor_image(Some(CustomCursorImage))` (egui 0.37) pushes an RGBA bitmap through `PlatformOutput::cursor_image` to the integration; egui-winit uploads it as a real OS cursor (bypasses the egui-window clipping a painter-drawn cursor would suffer) and dedupes by `Arc` pointer identity — keep ONE `Arc<[u8]>` alive and re-push it every frame cheaply. The bitmap is STRAIGHT (non-premultiplied) RGBA; `size`/`hotspot` are `u16`. Backends without custom cursors (web) silently fall back to the frame's `cursor_icon` — set both (`set_cursor_icon` + `set_cursor_image`) when the image matters (russet: the Eyedropper's pipette, `app/tool_icons.rs` + the canvas hover branch in `app.rs`).
- Wayland decorations: eframe 0.37 enables only `winit/wayland`, so winit falls back to sctk's `FallbackFrame` — its `set_title` is a NO-OP (the title is never rendered, even though eframe seeds it from the `run_native` app name and russet sends `ViewportCommand::Title`), and a title-bar click emits only `FrameAction::Move` (NO double-click-to-maximize logic at all); GNOME/Mutter draws no server-side decorations, so the window shows a bare bar with no title and a dead double-click (owner report 2026-11-16). The owner-approved `winit` dependency (SPEC §1) enables `wayland-csd-adwaita` → winit uses `AdwaitaFrame` instead: title text (system font preference with an embedded Cantarell fallback), Adwaita buttons, GTK-like 400 ms double-click maximize. Pure Rust — no flake.nix `runtimeLibs` change; inert outside Unix (winit gates sctk-adwaita by cfg(unix)).
