# eframe/egui 0.37 API quirks (verified against the installed crate)

The canonical home of the eframe/egui 0.37 API quirks — moved VERBATIM from
AGENTS.md (docs-compaction round). Each quirk keeps its fact + its fix; new
quirks are APPENDED here, never into AGENTS.md (see AGENTS.md "Maintenance").
Reading route: UI / windows / egui work → this file.

- `eframe::App` implements `fn ui(&mut self, ui: &mut egui::Ui, frame: &mut eframe::Frame)`; there is no `update` method.
- `egui::CentralPanel::default().show(ui, ...)` takes `&mut egui::Ui`, not `&egui::Context`.
- `egui` is not a direct dependency: `use eframe::egui;` (or fully qualify `eframe::egui`).
- Keyboard-focus guard is `ctx.egui_wants_keyboard_input()`, not `ctx.wants_keyboard_input()`.
- `Ui::id()` is deprecated; use `Ui::scope_id()`.
- `egui::Grid` floors EVERY column at `interact_size.x` (40 pt) regardless of the widgets inside (`grid.rs` `set_min_col_width(col, widget_rect.width().max(min_cell_size.x))`) — a compact grid of narrower widgets (e.g. 28 pt tool buttons) silently grows wide columns and a huge visible horizontal gap while the row gap obeys `spacing().y` (caught by pixel measurement 2026-11-18: 18 pt vs 6 pt). Fix: `.min_col_width(widget_width)` on the Grid builder.
- Panels are unified: `egui::Panel::top(id)` / `bottom` / `left` / `right`; there is no `TopBottomPanel`/`SidePanel`.
- Menu bar is `egui::MenuBar::new().ui(ui, |ui| { ui.menu_button(...) })`; there is no `egui::menu::bar`.
- The theme API SPLITS the choice from the active style: `egui::Theme` = {Light, Dark} only — there is NO `FollowSystem` variant (a compile error, caught 2026-11-18). The Dark/Light/System choice is `egui::ThemePreference`: `Context::set_theme(impl Into<ThemePreference>)` stores it, and `Context::theme()` returns the RESOLVED active `Theme` (what the icon atlas keys on); `Context::system_theme()` mirrors the OS.
- egui 0.37's color picker has NO hex/RGB text entry ANYWHERE: `color_picker_hsva_2d` renders only the R/G/B(/A) `DragValue` row (`srgba_edit_ui` — no text field), and `color_edit_button_srgba`/`_hsva` have none either (the hex format exists only in the accessibility `current_text_value`). russet adds its own per-well hex field under the picker (`windows/palette_window.rs::color_swell_button`, owner request 2026-11-19): the raw text lives in egui's `IdTypeMap` keyed per well (a frame-rebuilt string would fight the caret), it is re-seeded from the color on popup open / outside changes, parsed on edit through `launch.rs::parse_hex_components` (the launch-flag syntax, one primitive), and canonicalized `#RRGGBBAA` on blur. The syntax is JUNK-TOLERANT (owner request 2026-11-19: every non-hex-digit character is stripped before parsing, an optional `0x` prefix dropped first; the remaining DIGIT COUNT picks the form — 3 `RGB`, 4 `RGBA`, 5 `RGBAA`, 6 `RRGGBB`, 7 `RRGGBBA`, 8 `RRGGBBAA`; the owner calls the 5-vs-7 RGB-digit asymmetry deliberate). The short forms' alpha fallback is a per-well SEED alpha snapshotted with the text (the same re-seed branch): a live-typed longer entry passes THROUGH alpha-carrying prefixes (typing `FF7F00` hits the 5-digit form at `FF7F0`, whose own alpha briefly applies), and without the seed that prefix's alpha would leak into the final 6-digit color.
- Tool windows/panels are drawn with `egui::Window::new(...).show(&ctx, ...)`; input over them must not paint on the canvas (use response hover/occlusion, not raw pointer position).
- Title-bar drag of a `Window` is detected via `ctx.read_response(area_id.with("__title_click"))` (the same id `window.rs` uses internally).
- `Window::new(title)` derives the window's Id FROM THE TITLE (`window.rs` on `Window::new`: "This is true even if you disable the title bar") — a changing, hidden or EMPTY title MUST come with an explicit `.id(…)` or the identity (stored position!) resets; `Window::id`'s doc: "Required if the title changes, or is shared with another window". To keep the title BAR but hide only the LABEL, pass an EMPTY title string: `title_ui` builds the bar (button atoms + drag strip) from the bar itself regardless of the text, so `Window::new("").id(…)` renders a label-less bar (caught 2026-11-18, the Tools window — v4's `title_bar(false)` removed the whole bar, the owner wanted only the label gone). `title_bar(false)` itself removes the ✕/collapse buttons too, but the window STAYS movable: `WindowDrag::TitleBar` "silently falls back to `Self::Anywhere`" for title-bar-less windows.
- An auto-sized window's TITLE STRIP does not participate in the window's size (`title_ui` allocates a ZERO-width advance rect horizontally — `window.rs` "We may not allocate in the horizontal direction as that would break auto sizing") and is free to PAINT wider than the window itself. The strip's fixed width with BOTH buttons and an empty title = 2 button atoms (each as wide as the Heading row height — 20.7 pt at the default 18 pt Heading font) + 4 `item_spacing.x` gaps (8 pt each) + the strip frame's inner margin (the window frame's 6 pt per side) = 85.4 pt, against the Tools window's outer 76 pt (the 62-pt grid + frame margins) — the strip painted ~11 pt past the window's right edge and the ✕ landed half outside it (owner report 2026-11-19; pixel-measured headless AND under Xvfb). The per-window lever is `Window::title_frame(...)`: its inner margin is the strip's padding (egui re-applies the active `weak_bg_fill` on top of it itself, so a `Frame::NONE`-based title frame keeps its background), and `Margin` fields are `i8` in 0.37. russet's chosen fix (owner v6 2026-11-19, "variant A2"): `tools_window_builder` feeds `title_frame` with `Frame::window(&ctx.global_style())` whose `inner_margin.left/right` are zeroed (`app/windows.rs::tools_title_frame`) — the strip's minimum (73.4 pt) fits the grid-width window, so the strip paints EXACTLY the window's width and both buttons sit inside; the vertical padding stays (the strip's height, fill and rounded corners unchanged — the owner's variant A, `Margin::ZERO`, additionally shrank the strip vertically and shifted the first-open position; NOT picked). The regression test (`windows/tests/tools_strip.rs`) measures it headless: the strip's drag response `area_id.with("__title_click")` spans from the collapse ICON's right edge to the close ICON's left edge, and each ICON is its button atom shrunk by `(atom − icon_width) / 2` per side, so the atoms' outer edges are `click.min_x − (heading_row_height + icon_width) / 2` and `click.max_x + (heading_row_height + icon_width) / 2` — both must stay within the window (the default frame put the ✕ atom's edge ~4.4 pt past it).
- Window COLLAPSE (the strip's ▼ button or a title double-click): the state lives in `CollapsingState` under `area_id.with("collapsing")` (public path: `egui::collapsing_header::CollapsingState` — NOT `egui::CollapsingState`) and is `store`d EVERY frame right after the window content — so after `Window::show`, `CollapsingState::load(ctx, …)` already sees THIS frame's toggle. `Window::show` returns `Some(InnerResponse { inner: None })` exactly while the collapsing body is closed (openness 0; the show doc states it), which makes `response.inner.is_some()` the per-frame "body shown" flag — russet's settings-panel hide-while-collapsed guard keys on it (owner request 2026-11-19). A window with a stored `pivot` re-anchors AROUND the pivot point when its size changes: collapsing a `pivot(LEFT_CENTER)` window moves its top edge DOWN by half the height delta, so a click position taken from the expanded window misses the collapsed strip.
- Headless `Context::run_pass` texture counting (the atlas-lifecycle test): the FIRST pass uploads the app textures PLUS egui's font atlas (the count = the atlas's icon textures + 1 font — currently 33: 8 tool + 8 shape + 2 line + 6 select + 8 tree icons; owner request 2026-11-20 added the Select family, 2026-11-21 the tree row-size set); a ppp change re-uploads only the app textures (the font atlas uploads once); a theme change uploads exactly 1 (the font atlas follows the theme) — so a rebuild-vs-no-op discriminator is the count vs the expected app-texture count, not `== 0`.
- `egui::Rect` has NO `min_x`/`min_y`/`max_x`/`max_y` shorthand FIELDS — the only fields are `min: Pos2` / `max: Pos2`; the edge accessors are the METHODS `left()/right()/top()/bottom()` (plus `width()/height()/center()/…`). Caught 2026-11-20 (six `E0609` errors cost a cold gates-test compile in the gap test; logged in PROBLEMS.md).
- To move a `Window` programmatically (e.g. when a resize repositions a floating window), load `AreaState::load(ctx, area_id)`, call `set_left_top_pos`, and persist with `memory.areas_mut().set_state(LayerId::new(Order::Middle, area_id), state)` right after `Window::show` — `Window::current_pos` is discarded every frame in title-bar mode, and builder position calls would fight the drag.
- `Window::default_pos` applies only while the window's `AreaState` has no stored `pivot_pos` (fresh session; eframe's `persistence` feature is compiled in — owner request 2026-11-23 — but the AUTOMATIC save channels are off, `persist_window: false` in main.rs + `persist_egui_memory() -> false` in app.rs, so every launch is still fresh: window geometry and egui Memory are never written or read, and the one saved setting (the Mouse4/5 mode, §3.14/SPEC) is a single flat key that carries no window state. The feature's one unavoidable side effect is the startup-created data dir — `~/.local/share/russet` on Linux, `%APPDATA%\Russet\data` on Windows — EMPTY for a user who never decided a setting). Pair it with `.pivot(Align2::…)` to pin a corner/edge instead of the left-top: `pivot(LEFT_BOTTOM)` + `default_pos(content_rect().left_bottom())` = flush bottom-left. `set_left_top_pos` converts through the stored pivot, so §3.11 repositioning stays correct with any pivot.
- eframe 0.37 `persistence` save mechanics (verified against the installed crate, the settings round 2026-11-23): there is NO request-save API — `App::save` runs on the 30-s autosave (`App::auto_save_interval()`, overridable) and at exit (`save_and_destroy`), so a changed setting lands within ≤30 s or at quit. Native `FileStorage` marks the file dirty on EVERY `remove_string` but only on a VALUE CHANGE for `set_string`, and `flush` writes `app.ron` only while dirty — therefore: a repeated remove of an ABSENT key would still dirty+write the file every autosave (guard: remove only when `get_string` says the key is present), and an unchanged set is free. `eframe::set_value`/`get_value` (RON) need serde, which eframe does NOT re-export — adding `serde` to Cargo.toml would be a dependency-approval-flow decision; the zero-dependency path is plain `set_string`/`get_string` with hand-encoded values (russet encodes the Mouse4/5 mode as `"ask"`/`"always"`/`"never"` under `"settings/mouse_side_buttons"`). On web every Storage key becomes its OWN localStorage entry (and `persist_egui_memory: false` keeps `egui_memory_ron` unwritten).
- An `auto_sized()` `Window`/`Resize` sees `available_width()` = the whole `content_rect` on its FIRST layout pass (its `default_size` is INFINITY clamped to the screen), and its `desired_size` never shrinks below the first frame (`max(last_content_size)`). Any content width derived from `available_width` therefore opens the window screen-wide AND grows it one row-overflow per frame forever — the Layers window smeared past the main window this way (owner report 2026-11-13; full write-up at `app/layers_window.rs::LAYERS_DEFAULT_WIDTH`). Fixed-width rows + `default_width` (Layers now) or only content-hugging widgets (Tools/Palette) are stable; `available_width`-derived widths are safe ONLY in windows with a stored `default_width` (Tool Log).
- A PLAIN `Window` (not `.auto_sized()`) opens at egui's default outer size **340×420** (`window.rs` `Resize::default().default_size([340.0, 420.0])`), and its content's measured size never shrinks below what the first frame measured. Any scope that inherits the whole remaining available rect — e.g. a bare `ui.with_layout(...)` row — is anchored into that empty space (right/bottom per its layout), keeps the content min-size huge, and the dialog stays tall with its buttons detached below the fields (owner report 2026-11-15: dialogs stretched toward the main-window bottom edge; regression tests in `app/dialogs/tests.rs`). Bound such rows with `allocate_ui_with_layout(vec2(available_width(), row_height), …)` — safe in windows with a stored default width, NOT in `.auto_sized()` ones (quirk above). For dialogs that must ARISE centered on EVERY open (owner request 2026-11-15), `app/dialogs.rs::dialog_window` pins `pivot(CENTER_CENTER)` + `default_pos(content_rect().center())` and every close path calls `forget_dialog_position`, which overwrites the stored `AreaState` with a fresh one so the next open consumes `default_pos` again (`default_pos` is only ever consumed while the stored `pivot_pos` is None) — the dialog re-centers when reopened, yet stays draggable while open; the reset must run AFTER `Window::show` on the closing frame (the dialog's early-return skips all later frames, so nothing re-stores a position). egui's `Area::anchor(Align2, offset)` is the other tool — it is re-applied every frame AND makes the window immovable (`movable(false)`); right for permanently-fixed HUD-like windows, too rigid for dialogs, and it overrides egui's cascade `automatic_area_position` that would otherwise drop a new window slightly right/below of the existing ones.
- A headless-egui pass (`Context::run_pass`) paints NOTHING on a window's first pass — every shape arrives culled to `Shape::Noop` (the window is measured before its stored geometry exists); real shapes (`Shape::Text` runs included) appear from the SECOND pass on. Content-assertion tests (e.g. `app/dialogs/tests.rs::render_about_texts` joining `galley.job.text` per `Shape::Text`, recursing into `Shape::Vec` nests) must therefore run 2–3 passes and read the LAST one — the same "egui sizes a fresh window on the frame after its first layout" rule the plumbing tests follow.
- Textures die with their handles: `TextureManager` keeps a per-texture retain count, `TextureHandle::drop` decrements it (`TextureManager::free`), and a texture nobody holds is removed the SAME frame — the renderer then draws NOTHING where the stale `TextureId` was sampled (no warning, no white quad — silent emptiness). `Context::load_texture_cached` returns a handle like any other load; storing only the `TextureId` and dropping the handle freed the tool-icon atlas mid-run and rendered empty Tools buttons (caught by the visual-driver screenshot, owner request 2026-11-18). ALWAYS keep the `TextureHandle` alive for as long as the `TextureId` is sampled (russet: `app/tool_icons.rs::Atlas::handles`). Headless-egui tests do NOT catch this — the headless pass never rasterizes.
- Custom OS cursors: `Context::set_cursor_image(Some(CustomCursorImage))` (egui 0.37) pushes an RGBA bitmap through `PlatformOutput::cursor_image` to the integration; egui-winit uploads it as a real OS cursor (bypasses the egui-window clipping a painter-drawn cursor would suffer) and dedupes by `Arc` pointer identity — keep ONE `Arc<[u8]>` alive and re-push it every frame cheaply. The bitmap is STRAIGHT (non-premultiplied) RGBA; `size`/`hotspot` are `u16`. Backends without custom cursors (web) silently fall back to the frame's `cursor_icon` — set both (`set_cursor_icon` + `set_cursor_image`) when the image matters (russet: the Eyedropper's pipette, `app/tool_icons.rs` + the canvas hover branch in `app.rs`).
- Wayland decorations: eframe 0.37 enables only `winit/wayland`, so winit falls back to sctk's `FallbackFrame` — its `set_title` is a NO-OP (the title is never rendered, even though eframe seeds it from the `run_native` app name and russet sends `ViewportCommand::Title`), and a title-bar click emits only `FrameAction::Move` (NO double-click-to-maximize logic at all); GNOME/Mutter draws no server-side decorations, so the window shows a bare bar with no title and a dead double-click (owner report 2026-11-16). The owner-approved `winit` dependency (SPEC §1) enables `wayland-csd-adwaita` → winit uses `AdwaitaFrame` instead: title text (system font preference with an embedded Cantarell fallback), Adwaita buttons, GTK-like 400 ms double-click maximize. Pure Rust — no flake.nix `runtimeLibs` change; inert outside Unix (winit gates sctk-adwaita by cfg(unix)).
- A synthesized POINTER DRAG in a headless `run_pass` needs THREE passes and an immovable area: an auto-sized `Area`'s FIRST pass is a SIZING pass whose widgets are not registered for the next pass's hit-test (the sizing-pass quirk above, seen from the interaction side), and a MOVABLE area's own root widget (the `"move"` interact id, `Sense::DRAG`, first-pass rect = the whole screen) steals the drag binding at the press — the press then drags the AREA, not the widget. Recipe: `Area::new(id).movable(false).fixed_pos(…)` + `ui.allocate_rect(rect, Sense::click_and_drag())` (the allocated rect IS the content, so the area hugs and registers it), then TWO empty warm-up passes, the PRESS pass, the MOVE pass — `Response::dragged()` only turns true on the pass after the press hit-tested the widget. Caught 2026-11-25 driving the restored drag-pan regression test (`camera/tests/touch_pan.rs`).
- `InputState::multi_touch()` reports the two-plus-finger gesture (translation/zoom/rotation deltas over the touches' average), but egui's TouchState SEEDS a gesture only from a frame with a known POINTER position (`pointer.interact_pos` of the PREVIOUS pass — the web backend's primary touch drives the pointer, so the position always exists there): a headless touch test must feed a `PointerMoved` first, and finger add/remove frames carry a ZEROED `translation_delta` AND `zoom_delta` = 1.0 by design (the gesture re-baselines: `touch_state.rs` takes the CURRENT state as its own previous), so no debounce is needed. The pinch facts (verified against the installed 0.37.0 source, 2026-11-26): `zoom_delta` = the ratio of the touches' average pairwise distance (`avg_distance` — for two fingers, half their separation) to the previous frame's; `center_pos` is the CURRENT average position — a PREVIOUS center to anchor the zoom at must be tracked by the app itself (`camera.rs::TouchGesture::prev_center`); `zoom_delta_2d`/`rotation_delta` exist but russet does not use them. Verified headless and pinned by `camera/tests/touch_gesture_pass.rs` (`multi_touch_translation_pans_the_view`, `multi_touch_pinch_spread_zooms_the_view_at_the_gesture_center`, `a_move_and_spread_frame_zooms_and_pans_together`).
- eframe-WEB emulates a primary POINTER press on EVERY `touchstart` (verified against the installed 0.37.0 source, 2026-11-26: `eframe/src/web/events.rs::install_touchstart` → `input.rs::primary_touch_pos`): the FIRST touch of the surface becomes the pointer, a `Event::PointerButton{Primary, pressed:true}` is pushed BEFORE the Touch events of that touchstart, and it is pushed AGAIN for every LATER touchstart (with the PRIMARY touch's position — the pointer never jumps to the new finger). Two consequences for a touch paint app: (a) the first finger of every two-finger gesture paints through the ordinary pointer path, and (b) egui's multi-touch gesture engages only on the frame AFTER the second finger lands (`touch_state.rs::update_gesture` seeds from the PREVIOUS pass's `pointer.interact_pos` — with no prior pointer position, a simultaneous two-finger landing seeds nothing that pass). A zoom/pan attempt therefore leaves tool marks under a naive "suppress while gesture" rule: the marks are reverted at the second finger's raw landing frame (`app/input.rs::touch_takeover` — discard the in-flight stroke, REMOVE the session's nodes back to the pre-tap baseline, restore the baseline snapshot; see the third-pass quirk below for why the baseline must PRECEDE the tap's first press). The regression is pinned by REAL `draw_canvas` passes seeding the raw stream in the exact eframe-web shapes (`camera/tests/touch_takeover.rs`, `camera/tests/touch_takeover_web.rs`).
- The GESTURE-SEEDING DEPENDENCE is the trap (owner's second report 2026-11-26: a real phone's fingers land in DIFFERENT frames, and on his phone the gesture-based takeover misfired — "It got worse"): whether/when `multi_touch()` engages is the BACKEND's business (the seeding needs a prior pointer position; `TouchState::begin_pass` even reconciles `active_touches` as a persistent map, state not events). NEVER gate touch-session semantics (takeover, suppression) on the gesture — read the RAW `Event::Touch` stream from `i.raw.events` instead: `Start`/`End`/`Cancel` carry the id, a `Move` carries none, and a per-frame fold (`camera.rs::fold_touch_ids`) tracks the live ids exactly, immune to every seeding quirk. russet's `TouchGesture` keys the takeover on the raw 1→2 id transition (`TouchGestureFrame::second_finger`), poisons the session from that frame until the raw set empties, keeps egui's `any_touches()` as the reconcile authority (a missed end cannot wedge the session), and uses `multi_touch()` ONLY for the pan/zoom DELTAS. Verified headless in the exact no-pointer stream (`camera/tests/touch_takeover.rs::the_second_finger_reverts_the_stroke_with_no_gesture_at_all` — RED on the gesture-gated implementation) and in a real Chromium via CDP trusted touch + pixel diffs.
- THE WEB PIPELINE'S PER-TAP DOUBLE PRESS (owner's third report 2026-11-26, "nothing changed in my manual tests": a node still created, the fill applies twice on one finger): eframe-web installs BOTH `pointerdown` AND `touchstart` listeners on the canvas, and the browser fires them per physical tap in that order — `install_pointerdown` calls `runner.logic()` SYNCHRONOUSLY inside its own handler, so the tap's REAL pointerdown press runs a whole app pass BEFORE ANY `Event::Touch` exists; the following `touchstart` handler then pushes a SECOND, emulated press alongside the Touch start. Each press lands in its OWN egui pass, and egui's `PointerState` pushes a `PointerEvent::Pressed` for EVERY `Event::PointerButton{pressed:true}` without dedupe — so a stateless click tool (Fill) fires on BOTH passes ("the fill applies twice"), and the takeover's baseline latched on the touch session's BIRTH pass (the touchstart pass) sits one pass AFTER the fill's node — the revert could never cover it. Native winit is the contrast: egui-winit's `on_touch` emits the touch and its ONE emulated press in the SAME pass, so no bare press precedes it and a single dispatch happens. The fix is platform-free: a press observed while a touch is already down, AFTER a BARE press (no touch) was seen since the last quiet pass, is the web tap's duplicate — suppress its tool dispatch (`camera.rs::TouchGesture::bare_press_seen` → `TouchGestureFrame::press_duplicate`); the takeover baseline becomes a ROLLING latch at every quiet pass and every fresh bare press, always BEFORE the press's own dispatch (`App::touch_baseline`); the takeover itself removes the session's nodes (`remove_last`, NOT undo — an undo leaves a tree fork, and the owner's report was exactly "a new node is still created") and restores the baseline snapshot. All pinned by the staggered-stream tests (`camera/tests/touch_takeover_web.rs`) and verified in a real Chromium via CDP trusted touch: the event order was captured on-page (`pointerdown` before `touchstart`, finger 2's `pointerdown` after finger 1's `touchstart`), and two identical gestures — one with, one without a prior lone tap — produced pixel-identical post-gesture screenshots (the takeover reverted every mark; visualViewport stayed at scale 1, so the pinch was purely the app's own zoom/pan).
